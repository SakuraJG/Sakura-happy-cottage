# 代码审核标准

审核的目标不是确认代码“看起来能运行”，而是确认变更的行为、风险、验证证据和长期维护成本均可接受。批准表示审核者愿意对变更进入 `main` 负责。

## 审核顺序

1. 确认 Pull Request 只解决一个清晰问题，描述包含动机、范围和验证结果。
2. 从入口沿调用链检查到数据库、文件系统、邮件或外部边界，不能只看改动行。
3. 检查验证证据，确认命令、输入和预期结果可复现，并覆盖变更的核心路径。
4. 查看所有依赖和 workflow 变更，确认来源、权限、固定版本及供应链风险。
5. 检查 CI 结果和日志；不得以管理员绕过、重新运行偶发失败或跳过检查代替修复。
6. 用 `Approve`、`Comment` 或 `Request changes` 给出明确结论。

## 阻断条件

出现以下任一情况必须 `Request changes`：

- 可能导致认证绕过、横向越权、管理员提权、秘密泄露、SQL 注入、任意文件读写或存储型 XSS；
- 数据库迁移不可重复执行、可能破坏现有数据或缺少回滚/兼容说明；
- 新行为或缺陷修复缺少与风险相称、可复现且覆盖核心路径的验证证据；
- 提交包含真实配置、凭据、个人数据、数据库文件、附件、日志或 IDE 状态；
- workflow 使用宽泛写权限、未固定第三方 Action、向 fork PR 暴露 Secrets，或以 `pull_request_target` 执行贡献者代码；
- 引入已知中高危漏洞依赖，或依赖来源与许可证不清楚；
- CI 失败、审核对话未解决、最新代码未经过独立审核。

## 安全敏感检查

### 认证与会话

- 登录错误不能泄露账号是否存在；令牌必须使用密码学随机源并只存哈希。
- Cookie 保持 `HttpOnly`、合适的 `SameSite`，公网 HTTPS 部署必须启用 `Secure`。
- 修改或重置密码后撤销旧会话；一次性令牌必须过期且只能使用一次。
- 限流键、反向代理来源地址和内存增长风险得到考虑。

### 授权与数据隔离

- 每条备忘、附件和管理员查询都必须在服务端绑定当前用户或管理员角色。
- 不相信请求中的用户 ID、角色、文件路径或数据库归属字段。
- “资源不存在”和“无权访问”不能泄露其他用户资源是否存在。

### 输入、数据库与文件

- SQL 使用参数绑定，不拼接不可信字符串。
- JSON 拒绝未知字段和多段输入；文本、数字、日期、状态和大小均有限制。
- 上传文件名不能控制存储路径；使用随机存储名和排他创建，主动内容不能内联执行。
- 文件写入失败、事务失败和删除流程不会留下越权文件或不一致数据。

### 配置与部署

- 密码和 Token 从环境变量或秘密管理服务注入，不进入 Git、镜像层或日志。
- 容器保持非 root，基础镜像和依赖更新经过 CI 与漏洞扫描。
- 对外开放所需的 HTTPS、Cookie、数据库网络边界和文件权限有文档说明。

## 批准意见

批准时至少写明审查范围和证据，例如：

```text
已检查认证调用链、会话撤销和错误响应；按 PR 中记录的步骤验证成功、错误密码与过期令牌路径。构建、静态检查和 CI 通过，未发现阻断问题。
```

只写 `LGTM` 不适合作为安全敏感变更的最终审核记录。
